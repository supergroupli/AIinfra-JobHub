# 聘枢：从学习手册走向可复现作品与机会

核对日期：2026-11-13。本次为轻量产品调研，阅读了现有首页、阅读器、作品模板、PRODUCT.md 与 DEVELOPMENT_PLAN.md，并核对四个相关官方学习项目。以下“观察”指实际页面或源码可见内容；“判断”与目标数值是待验证的产品假设。本报告不推断市场份额、招聘效果或全球排名。

**核心建议：优先完成正在开发的实战项目库与作品档案生成器，并让它们共用一份工程证据结构。聘枢最值得验证的价值，是让一个人完成的实验更容易被另一个人复现、理解，并用于具体岗位交流。**

## 现有用户旅程与缺口

本轮开发前的源码快照已有 11 门十天双语课程、3 条职业路径、课程筛选、本地进度与笔记导出，以及下载作品模板和提交公开名片的入口。检查时 `content/jobs.json` 与 `content/people.json` 都为空。这个快照说明当前需要真实作品和参与者验证，不能把页面功能数量当成社区规模。

| 用户阶段 | 观察：已有能力 | 判断：最需要补的衔接 | 本轮应给出的结果 |
| --- | --- | --- | --- |
| 确定方向 | 有职业路径、先修、技术和硬件筛选 | 新人仍需把一串课程转成一个近期可完成的目标 | 按目标岗位与现有设备选一个项目，清楚看到第一份交付物 |
| 开始实践 | 每天有任务、验收和无 GPU 替代 | 环境不匹配时容易卡住；课程任务尚需自行组织成项目 | 明确支持环境、首个检查点、失败记录方式和替代路线 |
| 整理成果 | 阅读器保存笔记，可导出 Markdown；已有作品模板 | 从笔记到求职材料仍要手工拼装，容易遗漏自己的贡献与证据 | 项目选择后生成结构一致、可编辑的作品档案 |
| 获得反馈 | 已有 GitHub 讨论与公开名片入口 | 发布本身不产生复现或技术反馈 | 一个可领取的评审请求，以及具体、可回查的反馈 |
| 连接机会 | 有公开机会筛选和简历邮件入口 | 当前目录为空，无法检验招聘方是否理解作品或愿意回应 | 少量真实机会或自愿评审者，先验证阅读和交流是否有帮助 |

推荐的顺序是：**选项目 → 完成第一个检查点 → 留下代码和原始记录 → 生成作品档案 → 自愿提交评审 → 针对具体机会交流**。用户不必先学完所有课程，也不必公开求职意向才能获得学习价值。

## 四项竞争观察

| 官方项目 | 观察：页面实际展示什么 | 判断：聘枢可以怎样借鉴与区分 |
| --- | --- | --- |
| Hugging Face Learn | 学习入口包含 LLM、Agents、后训练、RL、音频等课程，以及开源 AI Cookbook；体现了广泛主题与生态资源的整合。[官方学习入口](https://huggingface.co/learn) | 聘枢应把有限维护精力放在推理、缓存、通信和平台工程的实验深度；引用官方资料，补充环境、测量、失败与作品组织，不重复建设通用 AI 百科。 |

| GitHub Skills | 官方入门练习通过复制到个人账号的仓库，带领学习者建立分支、提交文件、发起与合并 PR，最后形成 Markdown 作品。[官方练习仓库](https://github.com/skills/introduction-to-github) | GitHub 可以承载可见的学习过程，而不只是站点托管。聘枢可让项目成果保存在学习者自己的仓库，并用 Issue/PR 收集评审；提交次数本身不能代表能力。 |

这些观察只覆盖所列页面，没有据此声称其他平台缺少就业功能、没有工程课程或无法提供反馈。建议是从聘枢的用户与资源约束推导出的产品方向，不是已证实的竞争优势。

## 对正在开发的两条线的具体建议

### 实战项目库：先形成三个完整样例

项目库值得优先投入。先做好三种可用于岗位交流的项目，再根据复现反馈扩展数量：

| 项目方向 | 建议的最小问题 | 必须留下的证据 | 无对应硬件时的交付 |
| --- | --- | --- | --- |
| 推理服务与负载 | 固定一个引擎和模型，负载提高后 TTFT、完成时间与失败如何变化？ | 环境与版本、请求分布、逐请求记录、统计口径、至少一个失败或无收益结果 | 请求协议检查、公开或合成记录的指标计算；清楚标明数据来源 |
| KV 缓存复用 | 收益来自引擎本地缓存还是外部缓存，什么条件下取回比重算划算？ | 冷/热/隔离本地命中的对照、缓存取回证据、容量与成本假设 | 缓存身份测试、分层模型和成本敏感性分析；不冒充真实引擎基准 |
| 分布式传输与恢复 | 不同对象大小和并发下，传输是否正确，失败后哪些状态仍可信？ | 源/目的摘要、完成状态、版本与后端、原始数据、恢复步骤 | 受支持环境下的 CPU/TCP；否则提交明确标注的本地模拟与验证计划 |

每个项目首页至少回答：适合谁、需要什么设备、预计投入、第一步怎么开始、最终交付什么、如何自查。把关联课程链接到具体日课；不要要求读完多门课程才允许做第一项实验。

项目验收应围绕结果能否复查，而不是是否跑出某个预设加速比。负结果、文档修复、故障定位和严谨的模拟都可以成为作品，但证据类别必须准确。

### 作品档案生成器：减少整理工作，保留本人判断

生成器值得与项目库同时开发。建议两边共享以下字段，避免两套表单分别维护：

| 字段 | 对读者的作用 |
| --- | --- |
| 问题与目标岗位 | 明确作品解决什么问题、希望讨论哪类工作 |
| 固定环境 | 仓库与 commit、框架、模型 revision、硬件或模拟条件 |
| 原始证据与方法 | 代码、命令、配置、数据和统计口径；能找到结论的依据 |
| 本人贡献 | 区分自己的工作、合作部分和引用的上游实现 |
| 结果与限制 | 写清实测、模拟或设计；未执行的实验保留为待验证 |
| 下一步与可选联系 | 给评审者一个具体反馈问题，联系入口由本人决定 |

优先行为：选中项目后预填题目和交付要求；用户编辑后预览；导出 Markdown；再由用户选择复制到自己的 README 或提交公开名片。中英文输出要保留相同事实，无法可靠翻译的自由文本可保留原文并让用户编辑。

不要把勾选的学习进度自动写成掌握技术、工作年限或生产经验。未填写的实验值保持空缺或标为待补充。区分“本人报告”“有人做过代码评审”“有人复现了指定版本的结果”；只有真实存在相应链接时才展示后两项。

本地档案与公开名片应是两步。档案导出后立即有价值，公开与求职可以稍后决定。简历邮件入口继续独立，不将邮件内容自动变成公开 GitHub 数据。

## P0 / P1 / P2 优先级

| 优先级 | 建议 | 完成的判定 |
| --- | --- | --- |
| P0 · 当前迭代 | 完成上述三个项目样例，统一作品字段 | 每个样例都有首次检查点、官方来源、证据清单、版本要求和替代路径 |
| P0 · 当前迭代 | 打通项目 → 档案预填 → 预览/导出 → 自愿分享 | 一位新用户无需重新抄写项目要求，就能导出可读档案；纯静态站可完成 |
| P0 · 当前迭代 | 让十天阅读器直接跳到关联项目和档案 | 用户完成日课后看得到下一项具体工作；深链接带项目上下文 |
| P1 · 首轮试用 | 用少量志愿者完成项目，并征集具体复现/评审记录 | 先有独立反馈，再显示相应证据；记录最常卡住的步骤并修正 |
| P1 · 首轮试用 | 引入少量真实机会或招聘侧作品评审 | 核对来源、岗位约束与最近确认时间；评审者能准确理解本人贡献与限制 |
| P1 · 首轮试用 | 补学习记录/档案的导入恢复 | 导出文件能重新打开继续编辑，减少浏览器或设备更换造成的流失 |
| P2 · 有验证需求后 | 更多项目、多语言、可解释的作品与岗位交集 | 已有维护者和复现者；新内容有明确需求，不以条目数作为上线理由 |
| P2 · 有验证需求后 | 私密账号、跨设备同步、私信或订阅 | 有明确使用需求和相应身份/存储/服务方案后再开发 |

当前不优先增加排行榜、自动能力分数、课程完成证书或无法解释的招聘推荐。这些功能尚不能弥补项目缺少反馈和真实机会不足的问题。

## 两周如何验证

以下为**建议试验目标，不是现有指标或增长预测**。由维护者邀请 10 名自愿试用者，至少包含无 GPU 的学习者与已有工程经验者；另找 3 位工程师或招聘侧评审者。若招募不足，应如实报告人数，不能用页面浏览量补齐样本。参与者可以同时承担不同角色，但复现者不能就是作品作者本人。

| 问题 | 记录方法与分母 | 两周内建议目标 | 未达到时先改什么 |
| --- | --- | --- | --- |
| 能否顺利开始？ | 10 名已同意试用并启动项目的人，自愿回报首次检查点所需时间与阻塞原因 | 至少 7 人在第一次 60 分钟实践中留下可检查的第一份工件 | 缩小首次任务、补环境说明与 CPU 路径 |
| 能否形成作品？ | 同一组 10 人，统计具备问题、环境、证据、本人贡献和限制的档案 | 至少 4 份完整档案；下载空模板不算完成 | 简化项目范围、提高字段提示与示例质量 |
| 他人能否验证？ | 对提交的作品，记录第二个人使用的 commit、环境、操作及结果 | 至少 2 份作品有独立复现；模拟项目只验证其模拟范围 | 修复命令、输入和统计口径，补缺失原始数据 |
| 档案是否易读？ | 3 位评审者各看同一组自愿分享档案，回答“本人做了什么、证据在哪、限制是什么” | 至少 2 位能在每份 3 分钟内准确找到三项内容 | 调整摘要和证据位置，缩减无信息的自述 |
| 反馈是否真正到达？ | 对自愿提交的评审请求记录提交与首次实质回复时间；排除自动欢迎消息 | 首轮至少 3 次有具体建议的交流；同时报告响应时间与未回复数 | 先匹配维护者时间和请求范围，再承诺公开响应时限 |

第 1–2 天准备样例和档案入口；第 3–4 天让少量人先试，修正第一处阻塞；第 5–12 天完成项目和档案；第 13–14 天做独立复现与阅读测试。数据来自自愿反馈、公开项目和经同意的评审记录，不依赖隐藏追踪。样本很小，结果用于发现产品问题，不用于推断就业成功率。

## GitHub-only 的可行范围

GitHub 官方将 Pages 定义为从仓库发布 HTML、CSS、JavaScript 的静态托管服务。因此当前项目库、浏览器内档案生成与下载可以沿用已有静态架构；持续在线的私密应用服务不能由 Pages 本身提供。[GitHub Pages 官方说明](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages)

| 能力 | 现在可行的方式 | 产品边界 |
| --- | --- | --- |
| 项目与学习内容 | JSON/Markdown 经现有构建生成静态页面 | Git 保存教学文本与小型样例；模型与大型数据使用官方外链 |
| 档案生成 | 浏览器内表单、预览、本地保存、Markdown 导出 | 无需账号；本地状态不自动跨设备同步 |
| 公开作品 | 本人的仓库保存成果，Issue/PR 经维护者确认后收录 | 内容提交是主动公开流程，不能被描述为私密申请 |
| 同行评审 | 指定项目的 Issue/Discussion，链接到 commit 与证据 | 人工反馈的覆盖范围取决于真实维护者，不承诺无限答疑 |
| 两周指标 | 自愿试用登记、反馈模板和人工汇总 | 统计实际参与者与作品，不把访问量当成参与完成率 |
| 简历投递 | 保留 `career@yzinfra.com` 的邮件客户端入口 | 邮箱属于现有外部服务；GitHub 不托管该邮箱，接收能力由运营方确认 |

首轮增长也应围绕实际成果：每周分享一份有复现步骤的实验、一处失败原因和一条可操作反馈。先让学习者愿意带着作品回来，再扩大主题与地区覆盖。
